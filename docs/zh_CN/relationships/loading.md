# 加载策略 (Loading Strategies)

在使用关联关系时，选择合适的加载策略对应用性能至关重要。不同的加载策略适用于不同的使用场景。

> 💡 **AI提示词示例**: "ActiveRecord中的关联关系加载策略有哪些？它们各有什么优缺点？"

## 三种加载策略

框架提供三种关联加载方式，它们的差别在于**何时**执行查询、**加载多少**数据：

| 策略 | 触发时机 | 查询次数 | 适用场景 |
|------|----------|----------|----------|
| **延迟加载**（默认） | 首次访问关系时 | 每个对象各 1 次 | 不确定是否需要关系数据 |
| **预加载**（`with_()`） | 主查询执行时一并加载 | 每层关系 1 次 | 确定需要大部分对象的关系数据 |
| **批量加载**（概念） | 访问首个对象时 | 每层关系 1 次 | 需要兼顾两者 |

## N+1 查询问题

当遍历一个对象列表并逐一访问其关联关系时，会触发大量数据库查询，这就是著名的 N+1 问题。

```python
users = User.query().all()  # 1 次查询

for user in users:
    profile = user.profile()  # 每个 user 各执行 1 次查询（共 N 次）
```

- 若有 100 个用户，总查询次数 = 1 + 100 = 101 次
- 影响：数据库压力增大、网络延迟累积、应用响应变慢、连接资源消耗增加

**N+1 问题在循环中访问关系时最常出现**，预加载是它的标准解决方案。

## 延迟加载 (Lazy Loading)

默认情况下，关系是**延迟加载**的：只有调用关系方法时，才会执行 SQL 查询。

```python
user = User.find_one({'username': '张三'})  # 只查询用户本身
profile = user.profile()                    # 此时才查询资料
```

- 再次访问同一关系时不会重复查询——结果已被缓存
- **优点**：按需加载、节省内存、灵活性高
- **缺点**：循环访问时可能导致 N+1 问题、性能不可预测

**适用场景**：

- 不确定是否需要访问关联数据
- 只需要访问部分对象的关联数据
- 内存使用敏感、关联数据较大

> 💡 **AI提示词示例**: "延迟加载在什么情况下比较适用？使用时需要注意什么问题？"

## 预加载 (Eager Loading)

使用 `with_()` 方法在主查询中一并加载关联数据，是解决 N+1 问题的标准方案。

```python
users = User.query().with_('profile').all()  # 主查询 + 1 次关系查询
for user in users:
    profile = user.profile()  # 从缓存读取，不再触发查询
```

- 主查询执行后，框架会用一次批量查询加载所有用户的 `profile`
- 访问关系时直接从缓存读取，不触发额外查询
- **优点**：查询次数最少、性能最佳、可预测的数据库负载
- **缺点**：可能加载不必要的数据、内存占用较高

`with_()` 支持嵌套路径、查询修饰器、路径验证等完整规则，详见[预加载详解](eager_loading.md)。

## 批量加载 (Batch Loading)

**概念**：即便不使用 `with_()`，当访问列表中第一个元素的关系时，自动批量加载列表中所有其他元素的同一关系。

```python
users = User.query().all()
first_profile = users[0].profile()  # 理想情况：自动加载所有用户的资料
```

> **注意**：当前框架**不提供**隐式批量加载。框架的批量加载能力是通过 `with_()` 显式触发（见[预加载详解](eager_loading.md#加载机制)）。此处列出该概念仅为帮助理解预加载与延迟加载的折中方案。

## 选择建议

| 场景 | 策略 |
|------|------|
| 确定需要大部分对象的关系数据 | 使用 `with_()` 预加载 |
| 只需要少量对象的关联 | 使用延迟加载（默认） |
| 循环中访问关联数据 | 必须使用预加载 |
| 需要过滤/排序关联数据 | 预加载 + 查询修饰器 |
| 性能关键路径 | 优先考虑预加载 |
| 内存使用敏感 | 使用延迟加载 |
