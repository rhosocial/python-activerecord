Add read-only models via `ReadOnlyMixin` and the new `IReadOnlyBehavior` interface. A model that mixes it in declares `__read_only__ = True` and the framework refuses INSERT, UPDATE and DELETE issued through the model API, raising `ReadOnlyError` (a `DatabaseError` subclass, so existing handlers keep working) before any statement is prepared. Every write path is gated -- `save`, `delete`, `bulk_create`, `bulk_update`, `bulk_delete`, and `ActiveQuery.update_all` / `delete_all`, each in both the sync and async form -- while reads, relations, aggregation and counting are untouched. The feature is opt-in: a model that does not mix it in does not even answer `read_only()`, so existing behaviour is unchanged, and setting `__read_only__ = False` opts back out. `IReadOnlyBehavior` joins `IUpdateBehavior`, `IDeleteBehavior` and `IDataPreparationBehavior` in `interface/update.py`, and a single mixin serves both the sync and async models because `read_only()` is a zero-I/O classmethod. Read-only is orthogonal to the primary key: a read-only table may have an auto-generated key, and a keyless table may still be writable. Mixing in a write-event behaviour (`SoftDeleteMixin`, `TimestampMixin`, `OptimisticLockMixin`) is rejected when the class is defined, because those handlers could never run.
